Iron finds each track's BPM and musical key; Anvil writes them into the file's tags, and FableGear keeps a copy in its database. Skips files that already have tags — won't overwrite your Mix In Key work unless you ask it to.

How does it detect BPM and key?

Iron, FableGear's own detector, listens to the actual audio — not the filename — and finds the BPM and the musical key in one pass. The BPM is sanity-checked (30–300). Keys are written in Camelot notation. If Iron can't answer for a file, librosa (and essentia, if installed) step in as logged fallbacks.

Anvil, FableGear's tag reader and writer, saves the results into the file's tags and reads them back to verify. A copy also goes into the FableGear database. (Carrying BPM and key onto a Pioneer USB is still being built: the Record Room export doesn't pass them yet.)

Files that already have a BPM or key tag are skipped by default. Use the Re-detect toggles only if you want to replace existing values.

Optional MusicBrainz enrichment fingerprints each track via AcoustID and fills in missing title, artist, and album tags from the MusicBrainz database. Requires an AcoustID API key in settings.

What could go wrong?

This modifies the file tags (ID3, AIFF metadata etc.). Your audio waveform is untouched — unless Quench is switched on, which re-encodes the file to hit the target volume.

Edge cases to know about:

  • BPM detection can be fooled by very long intros or unusual time signatures. Review results in RekordBox afterward.
  • Key detection is an estimate — it works well on most house, techno, and disco, but can struggle with atonal or heavily processed tracks.
  • If a file can't be read (corrupt, DRM, unsupported format), it's logged as an error and skipped — it does not stop the rest of the batch.

What exactly happens to my files?

Each file is measured for integrated loudness (EBU R128). If it's outside −8.0 LUFS ± 0.5 LUFS, the file is re-encoded:

  • MP3 → re-encoded at 320 kbps CBR (a lossy encode cycle, even at 320)
  • AIFF/WAV → re-encoded losslessly at the same bit depth as the original

Files already within the window are left untouched. The original is renamed to .bak while the new file is written and checked; only then is the .bak deleted.

Only quench if uneven levels are a real problem for you. −8.0 LUFS is the usual DJ target. It is the one Forge step that changes the audio itself, so leave it Off for tag-only runs, and don't run it while Rekordbox is using the drive or during a gig.
